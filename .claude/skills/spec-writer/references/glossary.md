# 業務語彙 ↔ 実装語彙 翻訳ガイド

仕様書本文に書く言葉は **非エンジニアでも分かる** ものを優先する。実装語彙が頭に浮かんだら、本ガイドで業務語彙に翻訳してから書く。

## 原則

1. **業務語彙を主、技術用語は補助**: 仕様書本文の主役は業務語彙。どうしても技術用語が必要なら括弧書きで添える（例:「データベース（Firestore）」）
2. **画面 URL は OK**: 読み手が実際にアクセスできるパス（`/groups/[gid]`）は出してよい。ファイルパス（`src/app/...`）は NG
3. **数値は意味を添える**: 「7 日」ではなく「7 日（招待リンクの既定の有効期間）」
4. **略語は初出で展開**: 「PD」ではなく「プレイングディーラー（卓内で参加者がディーラーを兼任する役割）」

## ポーカー競技用語（ドメイン用語）— そのまま使ってよい

ターゲット読者がサークル運営者・参加者なので、ポーカー競技用語は基本そのまま使ってよい。初出で軽い説明があるとなお親切:

- ノーリミットテキサスホールデム（NLH）
- ストラクチャ（ブラインドの上昇スケジュール）
- ブラインド / SB / BB / アンティ
- レイズ / コール / フォールド / オールイン
- バスト（持ち点 0 で敗退）
- テーブルバランシング（卓間の人数調整）
- プレイングディーラー（PD）— 「卓内で参加者がディーラーを兼任する役割」
- ファイナルテーブル（FT）— 「最終卓・残り 1 卓」
- TDA ルール（Tournament Directors Association ルール）

## 「書かない方がよい」言い換えの例

実装視点の文 → 業務視点の文 の例:

- ❌ `finishTournament()` の `runTransaction` 内で `seasonStats/{uid}` を `tx.get` → `tx.set` で増分する
- ✅ トーナメント終了時に、各参加者のシーズン戦績（参加・優勝・FT・ポイント）が自動で更新される。途中で失敗した場合は何も変わらない
- ❌ players の self-create / organizer-clone 2 ブランチ
- ✅ 参加者は自分で受付できる。また運営担当者が「同じ参加者で次のトーナメントを作る」操作で、過去のトーナメントから参加者を引き継ぐこともできる
- ❌ `affectedKeys.hasOnly(['memberDisplayNames'])` で他フィールドの汚染を deny
- ✅ メンバーが自分の表示名を変更できるのみ。他人の名前や役割を勝手に書き換えることはできない仕組みになっている
- ❌ DRIFT WARNING: limits.ts と firestore.rules の値が drift している場合 npm run test:rules-limits で検出
- ✅ 1 卓あたりの席数の上限（10 人）など、一部の数値は複数の場所で連動する。設定変更時は仕様書の連動表を確認する（運営者が直接触る場面はほぼない）

## 残してよい技術用語の許容範囲

以下は **読み手のリテラシーに合わせて** 残してよい:

- ブラウザ名（Chrome / Safari / Firefox）
- スマホ / タブレット / PC
- URL / リンク
- アカウント / パスワード / サインイン
- データ / 設定
- バージョン / 更新

逆に、**避けたい** のは:

- フレームワーク名（Next.js / React / Tailwind）
- DB / コレクション / ドキュメント / クエリ / index
- API / endpoint / SDK / library
- transaction / batch / atomic
- schema / type / interface / enum
- aria / WCAG / WAI-ARIA
