# 個別 spec のテンプレート（解説版・業務向け）

`docs/specification/<NN>-<slug>.spec.md` に書く各セクションの目的・粒度・典型例を解説する。読み手は **非エンジニア** が標準。コピー用の最小フォームは [`assets/spec-skeleton.md`](../assets/spec-skeleton.md)。

## 文体の方針

- 主語は「運営者は…」「参加者は…」「サービスは…」のように人とサービスを主体にする
- 動詞は「できる」「設定する」「保存される」「表示される」など、操作・結果が想像できるもの
- 数値は **業務上の意味と推奨値** を添える（「8 名（1 卓の標準人数）」「30 日（招待リンクの最大有効期間）」）
- 技術用語が避けられないとき: 業務語彙を主、技術用語は括弧書き or 注釈（例: 「データベース（Firestore）」）。略号や関数名は出さない

業務語彙への翻訳例は [`glossary.md`](glossary.md) を参照。

## ファイル先頭 frontmatter

```yaml
---
title: <機能名（日本語）>
slug: <NN>-<feature-slug>
scope: <この spec が扱う範囲を 1 行で>
audience: <想定読み手。例: "サークル運営者・新メンバー">
relatedPrd: <.claude/PRPs/<NN>-<slug>/prds/...>  # 参考用。null 可
targetPhase: <PRD の Phase 進捗表で対応する phase 識別子。例: "Phase 4 完了時点">
lastUpdated: YYYY-MM-DD
status: stable | wip | needs-review
---
```

意図:

- `audience` で「誰向けに書いてあるか」を明示する。エンジニア向けにしてしまわないよう自分への戒めを兼ねる
- `targetPhase` / `lastUpdated` で「いつ時点の説明か」を明示する
- `status` は `wip` / `needs-review` を許容するが、その理由は本文末尾「既知の制約・未対応事項」に必ず記載する

## 1. 概要（Summary）

- 1〜2 段落で「この機能は何ができるか」「主にどんな人が使うか」「どの画面で操作するか」
- 抽象化しすぎず、具体化しすぎない。**読み手が他の spec を読まずにこの機能の輪郭を把握できる**程度

例:

> サークルへの参加と、運営担当者の役割を管理する機能。サークルのオーナーが招待リンクを発行し、リンクを受け取った人がサークルに参加できる。参加後はオーナーが運営担当者に昇格させたり、不要なメンバーを外したりできる。主に「サークル詳細」画面で操作する。

## 2. 想定利用シーン

ペルソナとシナリオで具体的に書く。技術的なテスト名（E2E spec の describe など）は本文に出さない — 業務シナリオの言葉に書き直す。

### 2.1 ペルソナ

- 例: 「20 人規模のサークル運営者（オーナー）」「初参加のゲスト」「複数サークル掛け持ちのオーナー」
- ペルソナごとに役割と主目的を 1 行で

### 2.2 シナリオ

最低 3 種類:

- **平常系（ゴールデンパス）** — 想定通り進む 1 シナリオ
- **代表的な失敗系** — 通信エラー / 招待リンク切れ / 同時編集 / 重複登録 など
- **運用イベント系** — 新シーズンの開始 / 役割の昇降格 / 設定変更 など（該当がない機能では省略可）

各シナリオは「いつ・誰が・どこから始める → どんな操作 → どうなる」の 5〜10 行程度。

例（平常系・失敗系・運用系の典型）:

> **平常系**: 新メンバー A さんが、運営者 B さんから受け取った招待リンクを開く → サインイン画面に飛ぶ → Google アカウントでサインイン → 自動的にサークルに参加して、メンバー一覧に名前が並ぶ。
> **失敗系**: 招待リンクの有効期限が切れていた場合、A さんは「このリンクは無効です」というメッセージを見る。B さんに再度発行してもらう必要がある。
> **運用系**: 運営担当者を増やしたいとき、オーナーは「サークル詳細」画面でメンバーの右にある「昇格」ボタンを押す。これで運営担当者として、トーナメントの作成や設定変更ができるようになる。

## 3. 機能要件（Functional Requirements）

**網羅性が最重要**。Phase 2 走査で抽出した画面・操作・設定項目を **1 つも漏らさず** 記述する。

機能ごとに次の 5 点をセットで:

### 3.x.1 何ができる機能か

- 1〜2 行で要約 → 詳細を箇条書きで（業務目線で「画面・操作・結果」を語る）
- 例: 「サークル名の変更。サークル詳細画面でオーナーがサークル名を入力し直して保存できる。新しい名前は全メンバーの一覧に即反映される。」

### 3.x.2 誰が・いつ使うか

- ペルソナ（運営者 / 参加者 / 招待ゲスト）と典型的なタイミング
- 例: 「主にサークル設立直後にオーナーが調整する。運営中の改名は稀」

### 3.x.3 なぜこの機能が必要か（Why）

- 「サークル運営の何の課題を解くか」「この機能がない場合の困りごと」を 2〜3 行で
- PRD の動機を **業務の言葉に翻訳** して引用（例: 「初期作成時に名前を間違えるケースがあるため」「年度替わりでサークル名を更新する習慣に対応するため」）
- 「便利だから」「あった方がいいから」は NG

### 3.x.4 設定項目とその意味

機能で運営者・参加者が指定できる項目を表形式で:

| 項目 | 入力形式 | 推奨 / 既定値 | 業務上の意味 |
| --- | --- | --- | --- |
| サークル名 | 文字列（最大 15 文字） | — | メンバー一覧やトーナメント名に表示される |
| 招待リンクの有効期間 | 日数 | 7 日（最大 30 日） | リンクが流出したときの被害範囲を限定するための期限 |
| 1 卓あたりの席数 | 整数 2〜10 | 8 名 | トーナメント新規作成時のデフォルト |

設定項目がない機能では本セクションを「該当なし」と書く。

### 3.x.5 注意点・制約

運用で踏みやすい落とし穴を箇条書きで:

- 1 度設定すると変更不可 / 追加できる人数の上限 / 同時実行できない操作 / 期限切れの扱い
- 例: 「最後のオーナーは脱退できません。脱退する前に他のメンバーをオーナーに昇格させる必要があります」

## 4. 権限・認可（必須セクション）

各個別 spec に **「誰が何の操作をできるか」の権限マトリクス** を必ず inline で記載する。overview や他 spec への委譲（「権限の詳細は overview を参照」「[02-circles-and-membership] を参照」）だけで済ませない。読み手はこの spec 単独で完結して権限を把握できる必要がある。

### 4.1 ロール別操作マトリクス

行は **具体的な操作**（業務語彙で）、列は **ロール**（業務語彙で。owner / organizer の英字をそのまま並べない）。

| 操作 | オーナー | 運営担当者 | 一般メンバー | ゲスト（匿名） |
| --- | --- | --- | --- | --- |
| <操作名 1> | ○ | ○ | × | × |
| <操作名 2> | ○ | ○ | ○ | × |
| <操作名 3> | ○ | × | × | × |

### 4.2 ロール定義（簡潔に）

各ロールが **この spec の文脈で何を意味するか** を 1 行で書く（overview の役割表とは別に、spec 内の用語として再定義）:

- **オーナー**: <この spec の機能で「オーナー」とはどういう人か>
- **運営担当者**: <同上>
- **一般メンバー**: <同上>
- **ゲスト（匿名）**: <該当する場合のみ>

### 4.3 補足（必要なら）

- 役割の昇降格は本 spec の対象範囲か、それとも `02-circles-and-membership.spec.md` を参照するか
- ロールが満たすべき前提条件（例: 「サインイン済みであること」「サークルに加入済みであること」）
- 権限の例外ケース（例: 「最後のオーナーは脱退できないが、それ以外の操作はオーナーと同じ」）

**書き方の注意**:

- 表のセルは ○ / × / △（条件付き）の 3 値で。条件付きの場合は表下に補足を書く
- spec の対象外の操作は載せない（例: 「シーズン戦績」spec に「招待リンク発行」を載せない）
- 同じ操作が他 spec にも登場する場合は、各 spec で **その spec の文脈に絞って** 再記載する。「重複」は冗長ではなく **読み手の作業負担を減らす設計**

## 5. 非機能要件（業務観点）

7 観点を**毎 spec で必ず取り上げる**。「該当なし」の場合は **「該当なし。理由: …」** と明記して空欄にしない。実装語彙（quota / AppError / runTransaction / aria-* など）は使わず、運用感覚の言葉で書く。

### 5.1 パフォーマンス（体感）

- ボタンを押してから何秒くらいで結果が出るか
- 同時に何人で操作しても大丈夫か
- 例: 「サークル名の変更は 1 秒以内に反映される。20 人規模なら同時操作の影響は出ない」

### 5.2 セキュリティ（運用方針）

- 誰が誰のデータを見られるか / 削除できるか
- パスワードの方式は何があるか
- 招待リンクの安全性
- 例: 「メンバー名はサークル内のメンバー全員に見える。サークル外の人には一切表示されない」

### 5.3 使いやすさ / アクセシビリティ

- キーボード・スマホ対応 / 文字サイズ / 色のコントラスト
- スクリーンリーダーで操作できるか
- 例: 「主要操作はすべてキーボードのみで行える。スマホのタップでも反応する」

### 5.4 信頼性 / エラー時の挙動

- 通信エラーが起きたとき何が表示されるか
- 同じ操作を二重に実行されたらどうなるか
- 例: 「招待リンクの発行中に通信が切れた場合、画面に再試行ボタンが表示される。二重登録は自動で検出されメンバー一覧に重複は出ない」

### 5.5 保守性 / 運用負担

- 設定の変更にどれくらいの手間がかかるか
- 設定値が連動する箇所（変更時に注意すべき場所）
- 例: 「1 卓あたりの席数のデフォルトを変更すると、それ以降に新規作成するトーナメントの初期値だけ変わる。既存のトーナメントには影響しない」

### 5.6 互換性

- どのブラウザ・端末で使えるか / モバイル対応の範囲
- 既存データはそのまま使えるか / 過去のサークルは移行が必要か

### 5.7 運用 / 観測性

- 何が記録されるか（操作ログ / エラー記録）
- 障害時に運営者が何を確認すればよいか

## 6. 既知の制約・未対応事項

- 現状で意図的に対応していない範囲（PRD で未着手の項目を業務目線で）
- 運用上踏みやすい落とし穴（招待リンク流出時 / 最後のオーナーの扱い 等）
- 将来の改善方針は短く（詳細は別 PRD で）

## 7. 関連 spec / ドキュメント

- 親 / 子の spec への双方向リンク
- 関連 PRD（参考: 設計の意思決定背景を知りたい人向け）
- 用語の翻訳ガイド: [glossary.md](glossary.md)

## 8. 網羅性チェック（spec 自身のチェックリスト）

末尾に**機械的に検証可能なチェックリスト**を残す。Phase 5 で再走査するときの手がかり:

```markdown
### 対応する画面 / 設定項目 / 想定利用シーン

- 画面: `/groups/[gid]`（サークル詳細）/ `/groups/[gid]/edit`（編集）
- 主な操作: サークル名変更 / 招待リンク発行 / 役割昇降格 / メンバー除外 / サークル削除
- 設定項目: サークル名 / 招待リンクの有効期間・最大利用回数
- 関連シーン: 「新メンバーの加入」「シーズン開始時の役割整理」「年度替わりの改名」
- 関連 PRD: <NN>-<slug>.prd.md の Phase X-Y
```

これにより、機能を更新したのに spec が更新されていない drift を後から検出しやすい。

## やってはいけないこと

仕様書本文・コード参照・引用すべてで以下は**避ける**:

- 関数名（`finishTournament`, `setIsPlayingDealer` など）
- ファイルパス（`src/lib/firebase/repositories/...`）
- SDK / クラス / 型名（`runTransaction`, `AppError`, `zodConverter`）
- セキュリティルール構文（`affectedKeys.hasOnly`, `request.auth.uid`）
- コミットハッシュ / Phase 番号の細部（"Phase 5.4" のような大区分は OK、"Phase 4.16 で発覚した既存バグ" のような実装履歴は除外）

詳細は [glossary.md](glossary.md) の翻訳例を参照。
