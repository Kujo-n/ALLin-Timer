# overview spec のテンプレート（業務向け解説版）

`docs/specification/00-overview.spec.md` に書く各セクションの目的と典型例を解説する。コピー用の最小フォームは [`assets/overview-skeleton.md`](../assets/overview-skeleton.md)。

overview は「個別 spec に行く前のランディング」。読み手は次のいずれか:

- **新メンバー / コラボレーター** — サービスの輪郭をまず把握したい
- **経営判断者 / 外部レビュアー** — 「このサービスは何ができるのか / どこまで進んでいるのか」を一覧で把握したい
- **将来の自分** — 個別 spec の索引として使う

このため overview は **個別 spec の内容を重複で書かず、索引と全体像に絞る**。

## ファイル先頭 frontmatter

```yaml
---
title: ALLin-PokerTimer 業務仕様書 — 全体像と索引
slug: 00-overview
scope: プロジェクト全体
audience: サークル運営者・経営判断者・新メンバー
relatedPrd:
  - .claude/PRPs/01-allin-timer/prds/01-allin-timer.prd.md
  - .claude/PRPs/02-season-stats-and-share/prds/02-season-stats-and-share.prd.md
targetPhase: <"全 PRD の進行中 phase 一覧" の文字列要約>
lastUpdated: YYYY-MM-DD
status: stable
---
```

## 1. サービス全体像

- 1 段落で「何のためのサービスか」（[CLAUDE.md](../../../CLAUDE.md) のプロジェクト概要を業務語彙に翻訳）
- 対象規模 / 配布形態 / ライセンス
- 主要ペルソナ（運営者 / 参加者 / ゲスト）

例:

> ALLin-PokerTimer は、20 人前後のサークル単位でノーリミットテキサスホールデム（NLH）のトーナメントを進行するための Web アプリケーション。熟練者がいなくても、TDA ルールに沿った席決めや卓間バランシングをアプリが自動で指示するため、月 1〜2 回のサークル開催を運営者 1 人でも回せる。MIT ライセンスで GitHub に公開されており、サークル固有のデータはクラウド上のデータベースにのみ保存される。

## 2. 想定ユーザーと役割（要約）

このセクションは **役割の存在と概念** を示すだけ。**操作粒度の権限マトリクスは各個別 spec の「4. 権限・認可」に inline で記載される**ため、ここでは詳細を書かない。

| ロール | この役割の役回り（1 行） |
| --- | --- |
| **オーナー** | サークルの最終責任者。すべての設定と役割管理を行える |
| **運営担当者** | トーナメント運営の実務担当。日常運営の主役 |
| **一般メンバー** | サークルに参加してトーナメントに出る人。設定は触らない |
| **ゲスト（匿名）** | 招待リンクから参加した一時利用者。アカウント情報を持たない |

各操作で誰が何をできるかは、該当する個別 spec を参照（例: サークル参加・脱退の権限は [`02-circles-and-membership.spec.md`](02-circles-and-membership.spec.md)、トーナメント運営の権限は [`03-tournaments.spec.md`](03-tournaments.spec.md) 等）。

非エンジニアが読むため、レイヤ図は描かず、**運用観点で意味のある情報** だけ書く:

| 領域 | 内容 |
| --- | --- |

## 5. 全体ポリシー

個別 spec で重複しがちな**横断的な方針**を 1 か所に書く。個別 spec は overview を参照する形にする:

### 5.1 セキュリティの考え方

- データベースは「既定では誰も触れない」設計。必要な人にだけ権限を開ける
- 公開リポジトリのため、サークル固有のデータはリポジトリに含めず、クラウド上のデータベースにのみ保存する
- サインイン方式: 匿名 / メール+PW / Google の 3 種類
- 招待リンク: 推測困難な文字列で発行され、有効期間と最大利用回数を設定可能

### 5.2 信頼性の考え方

- 通信エラーが起きた場合は画面にエラーメッセージが表示される
- 複数の更新が必要な操作は「まとめて確定」される（途中で失敗したら何も変わらない）
- 同時に同じ操作が走った場合の競合は、後勝ち / 弾く のいずれかに統一されている

### 5.3 使いやすさの考え方

- スマホ・タブレット・PC で同じように動作する
- 主要操作はキーボード・タップの両方で可能
- 文字サイズ・色のコントラストは見やすさを優先

### 5.4 運用の考え方

- 操作ログは保存される（運営者は普段は意識しない）
- 障害時の確認は運営者向けマニュアルを別途整備（現状は本仕様書末尾の「障害時の確認」を参照）

## 6. ガバナンス

### 6.1 言語

- 表示言語: 日本語のみ
- 仕様書・PRD: 日本語

### 6.2 ドキュメント間の対応関係

| ドキュメント | 場所 | 役割 |
| --- | --- | --- |
| PRD | `.claude/PRPs/<NN>-<slug>/prds/` | これから作るもの／作った理由（意思決定者目線） |
| **業務仕様書（spec）** | **`docs/specification/`** | **今このサービスはこう動く・こう設定できる（運用者目線）。本ドキュメント群** |

PRD は計画 / 意図、spec は現状記録。両者は補完関係で、片方が他方を置き換えない。

### 6.3 spec 更新トリガー

以下のときに本 overview および関連個別 spec を更新する:

- 新機能のリリース後
- 設定項目の追加 / 削除 / 既定値の変更後
- 既知のセキュリティリスクの状態が変わったとき

更新時は `targetPhase` / `lastUpdated` を必ず更新する。

## 7. 既知の全体制約

業務に影響する範囲だけを箇条書きで:

- 1 つのサークルあたりの想定規模: 6 卓以下 / 20 人前後
- 多言語対応: 日本語のみ
- モバイルアプリ（ネイティブ）は提供していない（Web のみ）
- 監視ダッシュボード / アラート: 未整備（運営者が手動で確認する）

詳細は各個別 spec の「既知の制約・未対応事項」を参照。
