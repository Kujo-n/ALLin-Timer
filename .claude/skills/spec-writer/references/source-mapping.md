# 入力ソース → spec セクション 対応表（業務向け）

Phase 4 の執筆中、「この情報はどこから持ってきて、spec のどのセクションに書くべきか」を即座に判断するための索引。

実装の細部（関数名・schema・rule 構文）は対象外。あくまで業務目線で「どこを見れば業務の意味が分かるか」を示す。

## 主な情報源と「業務向けに使う部分」

### PRD（`.claude/PRPs/<NN>-<slug>/prds/*.prd.md`）— 最重要

業務の意図・動機・対象規模・採用根拠が書かれている、もっとも業務に近い文書。Phase 2 で必ず全件 Read する。

業務向けに抽出する部分:

- **プロジェクト概要 / 核心価値 / 対象規模 / 想定ユーザー** → overview の 1 章
- **Implementation Phases 表（completed 行）** → 個別 spec の機能リスト
- **Implementation Phases 表（pending 行）** → 既知の制約
- **採用 / 却下した代替案** → 個別 spec の Why
- **受入基準** → 想定利用シーン
- **Technical Risks のうち業務に意味があるもの** → 注意点・制約

捨てる部分:

- 実装計画の詳細（plan ドキュメントのリンクなど）
- 設計判断のうち実装語彙が中心のもの（rule の構造、schema の構成など）

### 画面（`src/app/**/page.tsx`）

URL と「何の画面か」を抽出するためにファイル名と簡単な内容を見る。**ファイル名や内部のコンポーネント名は仕様書に出さない**。

業務向けに抽出する部分:

- URL パス（`/groups/[gid]` など、読み手にも見える）
- 画面のタイトル（h1 / page title）
- 画面の主な目的（運営者が何をするためのページか）
- 画面に表示される入力項目・ボタン（業務的に意味があるもの）

捨てる部分:

- React コンポーネント名 / hook 名
- import 文
- 内部の状態管理ロジック
- スタイリングの細部

### 横断ルール（`.claude/rules/*.md`）

業務に意味のある部分だけ抽出する。実装規約は対象外。

| ファイル | 業務向けの主要抽出ポイント |
| --- | --- |
| security-base.md | サークル固有データの保管方針 / 公開リポジトリ運用 |
| group-membership.md | **権限マトリクス（owner / organizer / member）が中核** / 招待コード設計原則（有効期間・使用回数）/ 既知のセキュリティリスク |
| firebase-patterns.md | **数値リミット一覧**（席数 2〜10 / 卓数 1〜6 / 文字数 15 / clone 50 件など）/ 既知の DRIFT WARNING（業務上の影響だけ） |
| その他（error-logging / security-env / testing） | 業務向けには対象外 |

捨てる部分:

- AppError ラップ / wrap helper / repository 経由の規約
- zodConverter / schema 定義
- 「allow update branch の `affectedKeys` 列挙」などの rule 構文の詳細

### E2E spec（`tests/e2e/**/*.spec.ts`）

`describe` / `test` 名から業務シナリオを抽出する。**実装テスト名はそのまま使わない** — 業務の言葉に書き直す。

業務向けに抽出する部分:

- `describe` 名から「何のシナリオを検証しているか」を読む
- 「いつ・誰が・何をして・どうなる」を業務の言葉で書き直す

捨てる部分:

- 個別の `expect(...)` 検証ロジック
- Page Object Model の構造
- Playwright の API 呼出

### 既存 spec（`docs/specification/<NN>-<slug>.spec.md`）

差分更新時に参照。新規生成時は無視してよい。

## 引用形式

PRD / rules を spec から引用するときは、**長文を貼らない**。要点を 1〜2 行に圧縮し、業務語彙に書き直して引用。出典は本文末尾の「関連 spec / ドキュメント」セクションでまとめる:

```markdown
## なぜこの機能が必要か（Why）

サークル運営において、年度替わりや組織変更でサークル名を変えたいという要望があるため、運営者が随時変更できるようにしている。変更後は全メンバーの一覧に即時反映される。
```

ではなく以下のような書き方は **避ける**:

```markdown
## なぜこの機能が必要か（Why）

PRD `01-allin-timer.prd.md` の Phase 2.5 「group based permission model」セクションで `groups/{gid}` collection の `name` field を additive に追加する際の動機として…
```

## 「載せない」判断の例

実装の細部に踏み込みそうになったら、以下のいずれかに該当しないか確認:

- 「読み手（非エンジニア）にとって、この情報が必要か？」
- 「この情報を消したら、運営判断や利用者の理解に支障が出るか？」
- 「この情報は業務語彙に翻訳できるか？」

3 つ目で **業務語彙に翻訳できないなら、そもそも spec に書く必要がない情報** の可能性が高い。
