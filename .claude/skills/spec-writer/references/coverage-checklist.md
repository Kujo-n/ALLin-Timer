# 網羅性チェック手順（業務向け）

「業務機能の漏れ」を減らすため、Phase 2 と Phase 5 で体系的に走査する手順を固定化する。**勘や記憶に頼らない**ことが本スキルの価値の核。

実装の細部（関数名・schema・rule 構文）には立ち入らない。あくまで「業務として何ができるか」を抽出する。

## 走査の基本方針

- すべて `Glob` / `Grep` / `Read` で機械的に列挙する
- 結果は in-context のメモに残し、Phase 3〜6 で参照する
- コードを読むのは「画面・操作・設定項目を抽出するため」。実装ロジックの精読は不要

## Phase 2: 業務機能の存在を列挙する

以下の 6 走査を順に実施し、業務機能リストを作る。

### 走査 1: PRD の業務意図（Why の源・最重要）

```
Glob: .claude/PRPs/**/prds/*.prd.md
```

各 PRD で次を抽出（実装手順・技術リスクは飛ばす）:

- **概要 / 対象規模 / 想定ユーザー** — overview の 1 章に直結
- **核心価値・解きたい課題** — 個別 spec の Why に直結
- **Implementation Phases 表のうち `completed` 行** — 業務機能として現存している項目
- **Implementation Phases 表のうち `pending` 行** — 既知の制約・未対応事項
- **採用 / 却下した代替案** — Why の補強

PRD はプロジェクトで最も「業務目線」で書かれているので、Phase 2 で最も重視する。

### 走査 2: 画面（URL → 機能境界）

```
Glob: src/app/**/page.tsx
```

各ルートで:

- **URL パス**（読み手にも見える）
- **何の画面か**（「サークル詳細」「トーナメント受付」「シーズンランキング」）
- **誰が見られる画面か**（運営者専用 / 参加者向け / 公開）

ファイル名やコンポーネント名は **読み手に出さない**。「どの URL でどんな画面が表示されるか」だけ抜き出す。

### 走査 3: 設定項目（数値・選択肢）

PRD と画面の両方から **運営者・参加者が指定できる項目** を列挙する。チェック観点:

- 数値項目（席数 / 卓数 / 持ち点 / レベル時間 / 招待リンクの有効期間 / 表示名の文字数 等）
- 選択肢（サインイン方式 / 役割 / 権限 / ストラクチャテンプレート選択 等）
- 任意 / 必須の区別
- 推奨値・既定値・最大値・最小値 と **その業務上の意味**

技術的な値域強制（rule の `affectedKeys` や zod の `.min().max()`）はそのまま転記しない。「2〜10 の整数で、標準は 8 名」のように業務語彙にして記述。

参考: [`source-mapping.md`](source-mapping.md) で「設定項目はどこから抜き出すか」を整理している。

### 走査 4: 想定利用シーン

E2E spec から業務シナリオを抽出する。**実装テスト名はそのまま使わない** — 業務シナリオの言葉に書き直す:

```
Glob: tests/e2e/**/*.spec.ts
```

各 `describe` / `test` 名から「いつ・誰が・何をして・どうなる」を読み取り、**業務シナリオの自然な日本語**に書き直す。

例:
- spec 名「anonymous-self-delete-flow.spec.ts → describe 'logout cancels deletion'」
- → 業務シナリオ: 「匿名ゲストでサインアウトした際、自動でアカウント削除が走るが、本人がキャンセルできる」

### 走査 5: 横断ルール（業務に意味のあるもの）

`.claude/rules/*.md` のうち、**業務として運営者に伝えるべき情報** だけ抽出する:

| Rule ファイル | 業務向けに抽出する情報 |
| --- | --- |
| security-base.md | 「サークル固有データはどこに保存され、誰が見られるか」 |
| security-env.md | （実装規約のため対象外） |
| error-logging.md | （実装規約のため対象外。ただし「ログレベル方針」だけは運用者向けに参考） |
| firebase-patterns.md | 「数値リミットの一覧」「連動して変わる場所」だけ抽出。実装パターン（wrap helper, converter）は対象外 |
| group-membership.md | **権限マトリクス（owner / organizer / member の何ができるか）が中核** / 招待コードの設計原則 / 既知のセキュリティリスク |
| testing.md | （実装規約のため対象外） |

実装規約系（AppError ラップ・logger.ts 経由・wrap helper・rules 構文）は **対象外**。

### 走査 6: 既知の制約・将来課題

`.claude/PRPs/<NN>-<slug>/prds/*.prd.md` の「pending」項目と、`.claude/rules/group-membership.md` の「既知のセキュリティリスク」節を集約する。これらは個別 spec の「既知の制約・未対応事項」と overview の「既知の全体制約」に転記する。

業務目線で書く（実装語彙は使わない）:

- ❌ "groupJoinCodes の `usesCount` 増分が rule で `>= 1` のみ強制で空消費 DoS 可能"
- ✅ 「招待コードの文字列が外部に流出した場合、悪意ある第三者が無効な使用回数を増やしてリンクを早期に使い切らせる嫌がらせが起こりうる。現状は最大利用回数が無制限の運用前提のため実害はないが、将来 UI から最大利用回数を設定可能にする際は要対策」

## Phase 2 走査結果のメモフォーマット

走査結果を作業 in-context に以下の表で残す:

```markdown
### 走査結果メモ

#### 業務機能リスト（PRD・画面・rules から）
- サインイン: 匿名 / メール+PW / Google
- アカウント削除（匿名ゲストの自動削除フロー含む）
- サークル作成・編集・削除
- 招待リンク発行・参加・脱退
- 役割管理（オーナー / 運営担当者 / 一般メンバーの昇降格）
- ストラクチャテンプレート（プリセット）
- トーナメント新規作成・受付・開催・終了・複製
- 席決め・卓間バランシング
- タイマー進行・休憩
- シーズン戦績集計・新シーズン開始
- ...

#### 画面（URL）
- /signin
- /groups/[gid]
- /tournaments/[tid]
- /tournaments/[tid]/clone
- ...

#### 設定項目（業務上の意味付き）
- サークル名（最大 15 文字、メンバー一覧やトーナメント名に表示）
- 招待リンクの有効期間（既定 7 日、最大 30 日）
- 1 卓あたりの席数（2〜10、標準 8）
- ...

#### 権限マトリクス（rules/group-membership.md から）
- 招待リンク発行: オーナー・運営担当者
- トーナメント作成: オーナー・運営担当者
- ...

#### 想定利用シーン（E2E spec から業務語彙に翻訳）
- 「初参加メンバーが招待リンクからサインインしてサークル参加」
- 「シーズン切替の運用」
- ...

#### 既知の制約
- 最後のオーナーは脱退できない
- 招待リンクの最大利用回数が現状 UI からは設定不可
- ...
```

これを Phase 3 で章立てに割り付け、Phase 4 で個別 spec に展開し、Phase 5 で再走査して取りこぼしを検出する。

## Phase 5: 最終検証チェックリスト

Phase 4 で書いた spec をレビューする。**すべての項目に明示的に answer する**:

### 業務機能の網羅性

- [ ] Phase 2 走査 1（PRD の機能リスト）の全項目が、いずれかの spec の「機能要件」に登場するか
- [ ] Phase 2 走査 2（画面 URL）の全項目が、いずれかの spec の「想定利用シーン」または「機能要件」で言及されているか
- [ ] Phase 2 走査 3（設定項目）の全項目が、いずれかの spec の「設定項目とその意味」に登場し、**業務上の意味付き**で書かれているか
- [ ] Phase 2 走査 4（想定利用シーン）の全項目が、いずれかの spec の「想定利用シーン」に反映されているか
- [ ] Phase 2 走査 5（横断ルール）のうち業務に意味のある情報（権限マトリクス等）が反映されているか
- [ ] Phase 2 走査 6（既知の制約）が overview または個別 spec の「既知の制約」に反映されているか

### 非機能要件 7 観点の網羅性

各個別 spec の「非機能要件」7 観点について:

- [ ] 観点が空欄になっていない（「該当なし。理由: …」も明示）
- [ ] 「該当なし」とした観点に対して理由が書かれている

### 5 点セット（業務機能ごと）

各機能要件サブセクションについて:

- [ ] 「3.x.1 何ができる機能か」が画面・操作・結果で書かれている
- [ ] 「3.x.2 誰が・いつ使うか」にペルソナが書かれている
- [ ] 「3.x.3 なぜこの機能が必要か（Why）」に PRD 由来の動機が **業務語彙で** 書かれている
- [ ] 「3.x.4 設定項目とその意味」が表形式で書かれている（または該当なしと明記）
- [ ] 「3.x.5 注意点・制約」が運用者目線で書かれている

### 権限マトリクス（個別 spec ごと）

- [ ] 個別 spec に「4. 権限・認可」セクションが存在する
- [ ] その中に **inline で** 「操作 × ロール」のマトリクス表が記載されている（overview や他 spec への委譲のみで済ませていない）
- [ ] マトリクスのロール列が業務語彙の日本語（オーナー / 運営担当者 / 一般メンバー / ゲスト）で書かれている。owner / organizer の英字をそのまま並べただけではない
- [ ] マトリクスの操作行は **その spec の機能範囲に対応するもの**（spec の対象外の操作を含めていない）
- [ ] ロール定義が spec 内の文脈で 1 行ずつ書かれている

### 用語チェック（業務語彙化）

[`glossary.md`](glossary.md) の翻訳テーブルと突き合わせて、以下が **混入していないか** 確認:

- [ ] 関数名（`finishTournament`, `setIsPlayingDealer` など）
- [ ] ファイルパス（`src/lib/firebase/repositories/...`）
- [ ] SDK / クラス / 型名（`runTransaction`, `AppError`, `zodConverter`）
- [ ] セキュリティルール構文（`affectedKeys.hasOnly`, `request.auth.uid`）
- [ ] 略語の未展開（"PD" 単独 / "FT" 単独 / "TDA" 単独 など、初出での説明なし）

### リンク健全性

- [ ] 個別 spec → overview のリンクが切れていない
- [ ] overview → 各個別 spec のリンクが切れていない
- [ ] 画面 URL の表記が実在パス（`/groups/[gid]` など）と一致している

### frontmatter

- [ ] 全 spec で `audience` / `targetPhase` / `lastUpdated` / `status` が埋まっている
- [ ] `status: wip | needs-review` の spec は本文末尾に理由が書かれている

すべて ✅ になるまで Phase 4 に戻って加筆する。**ここを省略すると本スキルの存在意義（網羅性最重要 + 非エンジニアに届く）が失われる**ため必ず実施する。
