# Spec Writer — 非エンジニアにも届く業務仕様書の生成

このスキルは **既に動いているサービスの「業務仕様」** を、非エンジニアでも理解できる粒度で `docs/specification/` 配下に生成・更新する。

## 何のための仕様書か

読み手は次のような人を想定する:

- **サークルの運営者・経営判断者** — 機能の使いどころと制約を把握したい
- **新しいメンバー / コラボレーター** — 何ができるサービスか、まずは輪郭を知りたい
- **将来の自分** — 「あれってどう動かすんだっけ」「なんでこの設定値なんだっけ」を素早く参照したい

このため仕様書は **業務目線・運用目線**で書く:

- ソースコード・SDK 呼出・関数名・schema 内部・rule 構文・migration 手順は **対象外**
- 画面 URL、操作の流れ、設定項目の意味、人数上限などの数値、想定利用シーン、なぜその仕組みになっているか の **業務的な意味づけ** が中心
- 用語は平易な日本語。技術用語が避けられない場合は短い注釈で言い換える（例: 「Firestore」→「データベース（Firestore）」）

PRD（`.claude/PRPs/<NN>-<slug>/prds/`）が「これから作るもの／作った理由」を意思決定者目線で記録するのに対し、本スキルが生成する仕様書は「**今このサービスはこう動く・こう設定できる**」を運用者目線で記録する。両者は補完関係。

## 起動条件

明示的に呼ばれたときだけ起動する:

- ユーザーが `/spec-writer` を実行した
- 「仕様書を作りたい／更新したい」「specification を整備したい」「業務仕様書」「非エンジニアにも読める仕様書」など、本スキルの目的そのものが言語化された

該当しない場合は次の代替を案内する:

| ユーザーの状況 | 推奨スキル / コマンド |
| --- | --- |
| 新機能を要件定義したい（forward） | `/prp-prd` |
| 実装計画を立てたい | `/prp-plan` |
| 直近差分のレビュー（技術視点） | `/code-review` |
| 全体構造のリファクタ | `/architect-refactor` |
| エンジニア向けの実装トレース仕様書が欲しい | （本スキルではなくコード参照型のドキュメント生成を別途検討） |

## 起動時の必須確認（4 点）

呼び出されたら、以下 4 点を**先に**確認してから Phase 1 に進む。曖昧な点が 1 つでもあれば短く質問する:

1. **対象スコープ** — プロジェクト全体 / 特定 PRD（`<NN>-<slug>`）配下 / 特定機能（slug 指定）/ 既存 spec の更新のみ
2. **既存 spec の有無** — `docs/specification/` 配下のファイル一覧を `Glob` で確認。既存 spec がある場合は「全面再生成」か「差分更新」かを確認
3. **読み手の前提知識** — 「非エンジニアの運営者」が標準だが、「経営判断者」「新メンバー」「外部レビュアー」のどこに合わせるかで用語の噛み砕き度合いが変わる
4. **粒度の合意** — 画面・操作の流れ・設定項目までは書く / コード参照リンクは載せない / 特定の業務シーン（例: シーズン切替の運用判断）を厚めに書きたいか

## 不変条件（Invariants）

ワークフロー全体を通じて **絶対に守る** ルール。違反したら作業を停止して報告する:

1. **読み手は非エンジニア**。SDK 名・関数名・schema・コミットハッシュ・rule の `affectedKeys` 構文・`runTransaction` などの**実装語彙はそのまま出さない**。意味を業務の言葉に翻訳して書く
2. **網羅性が最重要**。「機能の漏れ」を減らすため、Phase 2 の体系的走査（[`references/coverage-checklist.md`](references/coverage-checklist.md)）を必ず実施する。「たぶん全部書いた」で済ませない
3. **新機能を勝手に追加しない**。仕様書はあくまで現状の記録。改善提案・refactor 提案は仕様書末尾の「既知の制約・未対応事項」に留め、本文は現状の振る舞いを記述する
4. **日本語で記述**。プロジェクト規約（[CLAUDE.md](../../../CLAUDE.md)）に従う
5. **コードへの直接リンクは原則貼らない**。例外として「画面 URL（パス）」「PRD」「他の仕様書」へのリンクは可。ファイル単位（`src/lib/...`）・行番号（`#L42`）への参照は読み手の作業を増やすので避ける
6. **権限マトリクス（誰が何の操作をできるか）は個別 spec に記載する**。overview には全体ロールの一覧（役割名と要約）までに留め、操作粒度の権限表は **必ず関係する個別 spec の本文** に書く（外部 spec への委譲・参照だけで済ませない）。読み手は機能の細部を見にきた時に、その spec 内で誰が何をできるかを完結して把握できる必要がある

## ワークフロー

合計 7 Phase。Phase 2 と 5 が網羅性担保の核。

### Phase 1: スコープと既存 spec の把握

1. ユーザーから対象スコープを確定する（[`references/source-mapping.md`](references/source-mapping.md) で「どこから情報を拾うか」を確認）
2. `docs/specification/` 配下を `Glob` で一覧化し、既存 spec があれば最終更新日と対象 phase を読み取る
3. プロジェクト全体の概観を `.claude/PRPs/<NN>-<slug>/prds/<NN>-<slug>.prd.md` の冒頭（プロジェクト概要・対象規模・主要ペルソナ）から把握
4. 想定読み手と粒度を確認する（細かすぎる実装詳細は載せない / 抽象すぎて運営判断ができないものは避ける）

### Phase 2: 入力ソースの体系的走査（網羅性担保の核）

[`references/coverage-checklist.md`](references/coverage-checklist.md) の手順に従い、業務機能の存在を体系的に列挙する。記憶や勘で済ませない:

- **PRD 走査**（中心）— 各 PRD の「概要」「対象規模」「実装フェーズ表」「採用 / 却下した代替案」「Technical Risks」から **業務目線の機能リスト・採用根拠・対象外範囲** を抽出
- **画面（URL）走査** — `src/app/**/page.tsx` を `Glob` で列挙し、URL ごとに **何の画面か（運営者向け / 参加者向け / 設定画面）** をラベリング。ファイル名・コンポーネント名は読み手に出さない
- **設定項目走査** — 画面に存在する数値・選択肢を抽出し、**業務上の意味**を確認（例: 1 卓あたりの席数 = 「1 つの卓に座れる参加者の数。標準 8 名」）。技術的な値域強制は「2〜10 の整数」程度の表記に止め、`affectedKeys.hasOnly` などには触れない
- **想定利用シーン走査** — E2E spec（`tests/e2e/**/*.spec.ts`）の `describe` / `test` 名と PRD の受入基準から、**業務シナリオ**を抽出。実装の検証手順は出さない
- **横断ルール走査** — `.claude/rules/*.md` のうち**業務に意味のあるもの**だけを参照（例: 招待コードは何日有効か / メンバー名の文字数上限 / 数値リミットの値）。実装規約（`AppError` ラップ・logger.ts 経由・wrap helper）は対象外

走査結果は作業メモとして in-context に残し、Phase 3 以降の章立てを決める根拠にする。

### Phase 3: 章立ての設計

Phase 2 の結果から `docs/specification/` の章立てを決める:

- `00-overview.spec.md` — サービス全体像 / 想定ユーザー / 機能マップ / 全体ポリシー / 各 spec への索引（[`references/overview-template.md`](references/overview-template.md)）
- `<NN>-<slug>.spec.md` — 機能単位の個別 spec（[`references/spec-template.md`](references/spec-template.md)）
  - `<NN>` は 2 桁ゼロパディング sequential、`<slug>` は機能を表す英小文字 kebab-case
  - 番号は **読み手の自然な発見順序**（サインイン → サークル参加 → トーナメント開催 → シーズン戦績 等）で振る
  - 既存 spec を更新する場合は番号を変更しない（リンク切れ防止）

[`references/source-mapping.md`](references/source-mapping.md) で「PRD / 画面 / 利用シーンのどの情報が、spec のどのセクションに対応するか」の対応表を提示している。Phase 4 の執筆時に随時参照する。

### Phase 4: 個別 spec の執筆

[`assets/spec-skeleton.md`](assets/spec-skeleton.md) をコピーして個別 spec を埋める。各セクションの執筆指針:

#### 機能要件（網羅）

機能ごとに次の 5 点をセットで記載:

1. **何ができる機能か** — 1〜2 行で要約 → 詳細を箇条書きで（業務目線で。「この画面でこういう操作ができ、結果こうなる」）
2. **誰が・いつ使うか** — ペルソナ（運営者 / 参加者 / 招待ゲスト）と典型的なタイミング
3. **なぜこの機能が必要か（Why）** — 「サークル運営の何の課題を解くか」「ない場合の困りごと」を 2〜3 行で。PRD の動機を業務の言葉に翻訳して引用
4. **設定項目とその意味** — その機能で運営者・参加者が指定できる項目（数値・選択肢・任意/必須）と、それぞれの **業務上の意味と推奨値**
5. **注意点・制約** — 1 度設定すると変えられない / 同時に N 件まで / 期限切れの扱い等、運用で踏みやすい落とし穴

機能を**漏らさない**ため、Phase 2 の走査結果と必ず突き合わせる（個別 spec の末尾「網羅性チェック」セクションに対応する画面 URL・PRD 章・想定利用シーンのリストを残し、Phase 5 で再検証）。

#### 権限・認可（必須セクション）

各個別 spec に **「誰が何の操作をできるか」の権限マトリクス** を必ず inline で記載する。`docs/specification/00-overview.spec.md` 等の他 spec への委譲だけで済ませない（読み手はこの spec 単独で完結して権限を把握できる必要がある）。

書き方:

- 表形式で、行は具体的な操作（「サークル名を変更する」「招待リンクを発行する」「メンバーを除外する」など）、列はロール（オーナー / 運営担当者 / 一般メンバー / ゲスト）
- 業務語彙のロール名で（owner / organizer の英字をそのまま並べない）
- 該当 spec の機能範囲に出てくる操作だけを挙げる（spec の対象外の操作は載せない）
- 結合表として overview に総合一覧があってもよいが、**個別 spec のマトリクスは省略しない**

#### 非機能要件（業務観点）

7 観点を**毎 spec で必ず取り上げる**。「該当なし」の場合は「該当なし。理由: …」と明記して空欄にしない:

- **パフォーマンス（体感）** — 「ボタンを押してから何秒くらいで結果が出るか」「同時に何人で操作しても大丈夫か」レベル。技術的な quota は出さない
- **セキュリティ（運用方針）** — 誰が誰のデータを見られるか / パスワード方式は何があるか / 招待リンクの安全性。実装語彙は使わない
- **使いやすさ / アクセシビリティ** — キーボード・スマホ対応 / 文字サイズ / 色のコントラスト。WCAG 番号は出さなくてよい
- **信頼性 / エラー時の挙動** — 通信エラーで何がどう表示されるか / 同じ操作が二重実行されない仕組み（業務目線）
- **保守性 / 運用負担** — 設定の変更にどれくらいの手間がかかるか / 設定値が連動する箇所
- **互換性** — どんなブラウザ・端末で使えるか / 既存データはそのまま使えるか
- **運用 / 観測性** — 何が記録されるか / 障害時に運営者が何を確認すればよいか

#### 想定利用シーン

ペルソナとシナリオで具体的に書く:

- **ペルソナ** — 「20 人規模のサークル運営者」「初参加のゲスト」「複数サークル掛け持ちのオーナー」
- **シナリオ** — 平常系（ゴールデンパス）・代表的な失敗系（通信エラー / 招待リンク切れ / 同時編集）・運用イベント系（シーズン切替 / メンバー昇格）の 3 種を最低 1 件ずつ
- **トリガー** — 「いつ・どこから・どの操作で」この機能に到達するか
- E2E spec の `describe` / `test` 名は参考にするが、**spec 本文には実装テスト名を出さない**（業務シナリオの言葉に書き直す）

#### 既知の制約・未対応事項

- 現状で意図的に対応していない範囲（PRD で未着手の項目を業務目線で）
- 運用上踏みやすい落とし穴（招待リンクが流出した場合 / 最後のオーナーが脱退できない 等）
- 将来の改善方針は短く（詳細は別 PRD で）

### Phase 5: 網羅性の最終検証

Phase 4 で書いた spec が Phase 2 で列挙した「業務機能の存在」を漏らしていないか再走査する:

- 各個別 spec の本文と末尾の「網羅性チェック」セクションを突き合わせる
- Phase 2 で抽出した画面 URL / 設定項目 / 想定利用シーンのうち、**どの spec にも現れないもの**があれば章立てを見直す
- 各 spec の非機能要件 7 観点が空欄のまま「該当なし」になっていないか（理由付きの「該当なし」は許容）
- 用語が **非エンジニアでも分かる粒度** になっているか（実装語彙が混入していないか）の最終チェック

検証は [`references/coverage-checklist.md`](references/coverage-checklist.md) の最終チェックリストに従う。

### Phase 6: overview の生成・更新

[`assets/overview-skeleton.md`](assets/overview-skeleton.md) をコピーして `00-overview.spec.md` を埋める:

- サービス全体像（1 段落で「何のためのサービスか」「対象規模」）
- 想定ユーザーと役割
- 機能マップ（個別 spec への索引と一文サマリ）
- 全体ポリシー（言語 / 端末 / 配布形態 / セキュリティの考え方）
- 既知の全体制約

各個別 spec へのリンクは相対パスで、**spec が存在することを `Glob` で確認してから貼る**（リンク切れを残さない）。

### Phase 7: 整合性チェックと納品

仕上げに以下を確認:

- [ ] 全 spec の frontmatter（`lastUpdated` / `targetPhase` / `scope` / `audience`）が埋まっている
- [ ] 個別 spec → overview / overview → 個別 spec の双方向リンクが切れていない
- [ ] 機能要件の「何が / 誰が / なぜ / 設定 / 注意点」5 点セットが全機能で揃っている
- [ ] 各個別 spec に **権限マトリクス（操作 × ロール）** が inline で記載されている（外部 spec への委譲のみで済ませていない）
- [ ] 非機能要件 7 観点が全 spec で網羅されている（理由付きの「該当なし」も含めて）
- [ ] 想定利用シーンが平常系・失敗系・運用系の 3 種をカバー
- [ ] 実装語彙（関数名・SDK 名・コミットハッシュ・schema フィールド名・rule 構文）が混入していない
- [ ] commit message は CLAUDE.md 規約に従い日本語（type prefix のみ英語）

ユーザーに「どの spec を生成したか / どこを更新したか」を箇条書きで報告し、レビューを依頼する。
