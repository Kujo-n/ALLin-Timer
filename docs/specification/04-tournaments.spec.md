# トーナメント管理 業務仕様書

## 1. 概要

サークル単位でのトーナメント開催・進行を管理する機能。トーナメントには **「準備中 / 受付中 / 進行中 / 一時停止 / 終了」** の 5 つの状態があり、状態に応じて運営者ダッシュボードで使えるボタンが切り替わる。参加者は QR コードまたは URL で受付画面に来て、サインイン方式を選んで参加する。終了したトーナメントは「同じ参加者で次のトーナメントを作る」操作で複製できる。主に [/tournaments](/tournaments)・[/tournaments/[tid]](/tournaments/%5Btid%5D)・[/join/[tid]](/join/%5Btid%5D)・[/tournaments/[tid]/live](/tournaments/%5Btid%5D/live) で操作する。席決め・タイマー・音声通知の詳細は別 spec を参照。

## 2. 想定利用シーン

### 2.1 ペルソナ

- **運営担当者**: トーナメントを作成して当日運営する人
- **参加者（メンバー）**: 受付 QR でサインインして自席を確認する人
- **当日初参加のゲスト**: ゲスト匿名で受付 → 参加するライト勢
- **オーナー**: 全体の進行を見守りつつ、必要に応じて運営担当者の代わりに操作する人

### 2.2 シナリオ

#### 2.2.1 平常系: トーナメントの新規作成と受付

運営担当者 B さんが [/tournaments/new](/tournaments/new) を開く → トーナメント名は自動でデフォルト値「`[サークル名]トーナメント-X`」が入っている → ストラクチャを選択 → 1 Table あたりの席数を確認（サークル既定値が入っている）→ 「作成」を押す → [/tournaments/[tid]](/tournaments/%5Btid%5D) のダッシュボードが開く → 受付画面に QR が表示される → B さんが QR をスマホで読み取り、自分のスマホ画面に [/join/[tid]](/join/%5Btid%5D) が開く（または LINE で参加者にリンクを送る）。

#### 2.2.2 平常系: 参加者の受付（3 択フロー）

参加者 A さんが受付 QR を読む → [/join/[tid]](/join/%5Btid%5D) が開く → 「Google」「ゲスト」「メール+PW（既存）」から好きな方法を選ぶ → 表示名を確認・調整して「参加する」 → 受付完了画面に遷移 → ホスト側のダッシュボードに「A さん」が表示される。

#### 2.2.3 平常系: 同じ参加者で次回開催（複製）

終了したトーナメントの [/tournaments/[tid]](/tournaments/%5Btid%5D) で運営担当者が「同じ参加者で次のトーナメントを作る」リンクを押す → [/tournaments/[tid]/clone](/tournaments/%5Btid%5D/clone) が開く → 元のストラクチャが初期選択された状態で、参加者リストにチェックボックスが並ぶ（バストした人は OFF 既定）→ 続けたい人だけチェック → 別ストラクチャに切り替えても OK → 「作成」を押すと新トーナメントが「準備中」状態で作成され、参加者がコピーされる。

#### 2.2.4 失敗系: 受付の二重登録防止

A さんが受付完了したあとに、誤って再度 [/join/[tid]](/join/%5Btid%5D) を開く → 「すでに参加済みです」と表示される → 重複登録は起きない（同じ ID で 2 回目の登録は弾かれる）。

#### 2.2.5 失敗系: 一般メンバーが新規作成にアクセス

一般メンバーが [/tournaments/new](/tournaments/new) を直接 URL で開こうとする → 自動的に [/tournaments](/tournaments) にリダイレクトされる。

#### 2.2.6 運用系: 終了済みトーナメントの削除

運営担当者が、不要になった終了済みトーナメントを削除 → 確認ダイアログ → 削除実行 → 紐づく参加者・卓・イベント記録もまとめて消える（一括処理）。

## 3. 機能要件

### 3.1 トーナメント新規作成

#### 3.1.1 何ができる機能か

- [/tournaments/new](/tournaments/new) で新規トーナメントを作成
- 入力項目: 名前 / ストラクチャ選択 / 1 Table あたりの席数
- ストラクチャはサークル内のものから選ぶ（事前に [/structures](/structures) で作成しておく）
- 名前のデフォルトは「`[サークル名]トーナメント-X`」（X = 終了済みトーナメント数 + 1）
- 1 Table あたりの席数のデフォルトはサークル設定の値（既定 8 名）
- 作成すると **準備中** 状態で [/tournaments/[tid]](/tournaments/%5Btid%5D) に遷移

#### 3.1.2 誰が・いつ使うか

- 運営担当者・オーナーがトーナメント開催前

#### 3.1.3 なぜこの機能が必要か（Why）

「定期開催を支える運用主軸」のため、トーナメント作成の摩擦を最小化する。デフォルト値（名前の連番・席数）を整えることで、毎回の入力負担を減らしている。

#### 3.1.4 設定項目とその意味

| 項目 | 入力形式 | 推奨 / 既定値 | 業務上の意味 |
| --- | --- | --- | --- |
| 名前 | 文字列 | `[サークル名]トーナメント-X` | 一覧画面で識別する文字列 |
| ストラクチャ | サークル内ストラクチャから選択 | — | ブラインド進行スケジュール |
| 1 Table あたりの席数 | 整数 2〜10 | サークル既定値（既定 8） | 卓を編成する基準人数 |

#### 3.1.5 注意点・制約

- ストラクチャを未作成の状態だと作成できない（先に [/structures](/structures) で 1 件以上作る）
- 一般メンバーはアクセス不可
- 作成後でも準備中状態のうちは編集可能（[/tournaments/[tid]/edit](/tournaments/%5Btid%5D/edit)）

### 3.2 トーナメント一覧

#### 3.2.1 何ができる機能か

- [/tournaments](/tournaments) で、自分が所属するサークルの全トーナメントを一覧表示
- カードの色で状態（準備中 / 受付中 / 進行中 / 一時停止 / 終了）を区別
- 各カードを押すと該当トーナメントのダッシュボード or 参加者画面に遷移する
- 一般メンバーは「受付完了している自分のトーナメント」を中心に表示される

#### 3.2.2 誰が・いつ使うか

- 全メンバーが、過去・現在のトーナメントを確認したいとき

#### 3.2.3 なぜこの機能が必要か（Why）

サークル内のトーナメント開催履歴を一覧で把握できる単一画面が必要なため。状態の色分けにより、開催中のものをすぐ見つけられる。

#### 3.2.4 設定項目とその意味

該当なし（一覧のみ）。

#### 3.2.5 注意点・制約

- 表示されるのは現在選択中のサークルのトーナメントのみ
- サークルを切り替えると一覧が変わる（左のサイドバーまたはコンテキストで切替）

### 3.3 受付（参加者の登録）

#### 3.3.1 何ができる機能か

- [/join/[tid]](/join/%5Btid%5D) を開くと、3 つのサインイン方式から選んで受付する
  - **Google でログイン**: 既存の Google アカウント または 新規で
  - **メール+PW でログイン**: 既存アカウントの方
  - **ゲスト参加**: 表示名のみ入れて即参加（匿名）
- 表示名は自動で前回のものが入っており、編集も可
- 「参加する」を押すと受付完了
- すでに参加済みなら自動で受付完了画面に飛ぶ
- 受付後に「キャンセル」ボタンで自分の参加を取り消すこともできる（自席はあとで他人に再割り当てされる）

#### 3.3.2 誰が・いつ使うか

- 参加者全員（運営担当者の自己参加 / 一般メンバー / 当日初参加のゲスト）

#### 3.3.3 なぜこの機能が必要か（Why）

**運営者は手動で参加者を登録しない**（運営の負担を最小化）ため、参加者本人が自分でサインインして受付するセルフサービス設計になっている。サインイン方式が 3 種類あるのは、参加者の事情（既存アカウント有無 / アカウント登録抵抗）に対応するため。

#### 3.3.4 設定項目とその意味

| 項目 | 入力形式 | 推奨 / 既定値 | 業務上の意味 |
| --- | --- | --- | --- |
| 表示名 | 文字列、1〜15 文字 | 前回値（あれば） | 席表・参加者一覧に表示 |
| サインイン方式 | Google / ゲスト / メール+PW | Google を推奨 | アカウントと参加履歴の連携性 |

#### 3.3.5 注意点・制約

- 受付後に自分でキャンセル可能（参加者本人のみ）
- 運営担当者・オーナーは他人の参加を解除できる（後述）
- レイトエントリー締切レベルを超えると新規参加は不可（自動的に弾かれる）
- 同じユーザーが二重登録しようとすると弾かれる

### 3.4 運営者ダッシュボード

#### 3.4.1 何ができる機能か

- [/tournaments/[tid]](/tournaments/%5Btid%5D) で、運営担当者・オーナーがトーナメントを進行
- 表示構成（3 列レイアウト）:
  - **左**: 受付 QR（受付期間中）
  - **中央**: タイマー表示 + ブラインド情報 + 操作ボタン
  - **右**: 次の休憩までの時間 / 平均持ち点 / 残人数の 3 カード
- 下段: ストラクチャの情報 / 席表 / バランシング指示 / 参加者一覧 / バストボタン
- ボタンは状態に応じて切り替わる
  - 準備中: 「席を決定」ボタン / 編集 / 削除
  - 受付中: 「トーナメント開始」/ 編集 / 削除
  - 進行中: 一時停止 / 次レベル / 巻戻し / バストボタン / 全画面表示 / Table 名編集
  - 一時停止中: 再開
  - 終了: Winner 演出 / 「同じ参加者で次のトーナメントを作る」/ 削除
- ヘッダーにトーナメント名がページタイトルとして表示される

#### 3.4.2 誰が・いつ使うか

- 運営担当者・オーナーが当日の運営中

#### 3.4.3 なぜこの機能が必要か（Why）

「熟練者不在でも回せる」をコンセプトに、運営者が状態に応じて何をするべきかをダッシュボードがガイドする設計。1 画面で状態確認・操作・席表確認がすべて完結する。

#### 3.4.4 設定項目とその意味

該当なし（操作画面）。詳細な設定は [/tournaments/[tid]/edit](/tournaments/%5Btid%5D/edit)（準備中のみ）で行う。

#### 3.4.5 注意点・制約

- 一般メンバーは閲覧不可（自動的に [/tournaments/[tid]/live](/tournaments/%5Btid%5D/live) にリダイレクト）
- 編集ボタンは準備中のみ表示
- 削除ボタンは準備中または終了状態のみ表示

### 3.5 参加者向け表示（[/tournaments/[tid]/live](/tournaments/%5Btid%5D/live)）

#### 3.5.1 何ができる機能か

- 参加者・観戦者向けの全画面表示
- タイマー / ブラインド / 自席（参加者の場合）/ 残人数 / 次の休憩までの時間 を表示
- 操作ボタンは表示されない（読み取り専用）
- 自分の席が変わると「席が移動しました」というバナーが出る
- ゲスト匿名は受付完了後はこの画面に来ない設計（受付完了画面のみ）

#### 3.5.2 誰が・いつ使うか

- 参加者が、自席や現在のブラインドを確認したいとき
- 会場の大きなディスプレイに投影することで、複数卓全員が時刻を確認できる

#### 3.5.3 なぜこの機能が必要か（Why）

「複数テーブル進行時に PC 画面が見えない席で、ブラインドの変化に気付けない」課題への直接解決。各参加者がスマホで常時確認できる設計と、会場 PC で大画面投影する設計の両方に対応する。

#### 3.5.4 設定項目とその意味

該当なし（読み取り専用）。

#### 3.5.5 注意点・制約

- ゲスト匿名は受付完了画面に留め、live 画面には進ませない
- 全画面投影専用ではないため、操作ボタンが必要な場合は運営者ダッシュボードを使う

### 3.6 トーナメントの編集（準備中のみ）

#### 3.6.1 何ができる機能か

- [/tournaments/[tid]/edit](/tournaments/%5Btid%5D/edit) で、準備中状態のトーナメントの基本情報を編集
- 編集できるのは: 名前 / ストラクチャ / 1 Table あたりの席数
- 進行中・終了状態では編集不可（編集ボタンが消える）

#### 3.6.2 誰が・いつ使うか

- 運営担当者が、作成直後に修正したいとき
- 受付開始前に席数を変更したいとき

#### 3.6.3 なぜこの機能が必要か（Why）

作成直後に「やっぱり別ストラクチャにしたい」「席数を変えたい」というケースに対応するため。進行中・終了は編集禁止にすることで、開始後の意図しない変更を防ぐ。

#### 3.6.4 設定項目とその意味

3.1 節と同じ。

#### 3.6.5 注意点・制約

- 進行中の編集は別経路（レベル時間の動的変更）になる。詳細は [06-timer-and-blinds.spec.md](06-timer-and-blinds.spec.md)
- 一般メンバーはアクセス不可

### 3.7 トーナメントの複製（同じ参加者で次回作成）

#### 3.7.1 何ができる機能か

- 終了状態のトーナメントから [/tournaments/[tid]/clone](/tournaments/%5Btid%5D/clone) を開く
- 元のストラクチャが初期選択された状態で、ストラクチャを切り替え可能
- 参加者リストがチェックボックスで並ぶ（バストした人は OFF 既定、続けたい人にチェック）
- 「作成」を押すと新トーナメントが **準備中** 状態で作成される
- 選択された参加者は新トーナメントの参加者として一括コピーされる（最大 50 人まで）

#### 3.7.2 誰が・いつ使うか

- 運営担当者が、同じメンバーで 2 回目を開催したいとき
- 「会場の制限時間で 1 ストラクチャしか終わらず、2 回目は短縮版にしたい」というケース

#### 3.7.3 なぜこの機能が必要か（Why）

サークル運営でよくある「2 戦目の素早い立ち上げ」に対応するため。手動で 1 人ずつ受付をやり直す手間を削る。1 戦目の参加者リストを引き継ぐことで、運営者が新しい QR を配布する手間も減る。

#### 3.7.4 設定項目とその意味

| 項目 | 入力形式 | 推奨 / 既定値 | 業務上の意味 |
| --- | --- | --- | --- |
| 元のトーナメント | URL から自動 | 自動 | コピー元の参加者リスト |
| ストラクチャ | サークル内から選択 | 元のものが初期選択 | 新トーナメントのブラインド進行 |
| 名前 | 文字列 | デフォルト連番 | 新トーナメントの名前 |
| 1 Table あたりの席数 | 整数 2〜10 | 元のもの or サークル既定 | 卓編成基準 |
| 引き継ぐ参加者 | チェックボックス | バスト=OFF / 残存=ON | 何人連れていくかの選択 |

#### 3.7.5 注意点・制約

- 一度の複製で最大 50 人まで（過去最大規模を超える運用は想定外）
- 元のトーナメントが「準備中」状態のもののみ複製対象（新トーナメント）に追加可能
- 元の席表・卓設定はコピーされない（新トーナメントは席が空の状態で始まる）
- 一般メンバーはアクセス不可

### 3.8 トーナメントの削除

#### 3.8.1 何ができる機能か

- 運営者ダッシュボードから「削除」ボタンを押すと、確認ダイアログ → 削除
- 削除されるのは **準備中** または **終了** 状態のトーナメントのみ
- 進行中・一時停止中は削除不可（誤操作で進行中を削除しないため）
- 削除すると参加者リスト・卓設定・イベント記録もまとめて消える

#### 3.8.2 誰が・いつ使うか

- 運営担当者がテスト用に作ったトーナメントを片付けたいとき
- 終了済みの古いトーナメントを整理したいとき

#### 3.8.3 なぜこの機能が必要か（Why）

不要な記録を整理するため。誤操作で進行中を消さないよう、削除可能な状態を制限している。

#### 3.8.4 設定項目とその意味

該当なし。確認ダイアログのみ。

#### 3.8.5 注意点・制約

- 削除は復元不可
- 進行中・一時停止中は削除ボタンが表示されない
- シーズン戦績の集計は終了時点で確定済みのため、削除しても戦績には影響しない（仕様）

### 3.9 自分の参加をキャンセル

#### 3.9.1 何ができる機能か

- [/join/[tid]](/join/%5Btid%5D) の受付完了画面で、参加者本人が「キャンセル」ボタンで自分の参加を取り消せる
- 受付期間中・席決め前のキャンセルは席にも影響しない
- 席決め後のキャンセルは、その席が空になる（運営者の手動席編成で対応）

#### 3.9.2 誰が・いつ使うか

- 参加者が「やはり今日は参加できない」と判断したとき
- ゲスト匿名でも実行可能

#### 3.9.3 なぜこの機能が必要か（Why）

参加者が自分で取り消せることで、運営者の手動操作の負担を減らすため。

#### 3.9.4 設定項目とその意味

該当なし。

#### 3.9.5 注意点・制約

- 進行中・終了済みのトーナメントからは取り消せない
- 運営者は他人の参加を「除外」できる（バストとは別経路）

## 4. 権限・認可

### 4.1 ロール別操作マトリクス

| 操作 | オーナー | 運営担当者 | 一般メンバー | ゲスト（匿名） |
| --- | --- | --- | --- | --- |
| トーナメント新規作成 | ○ | ○ | × | × |
| トーナメント一覧の閲覧 | ○ | ○ | ○ | × |
| トーナメント編集（準備中） | ○ | ○ | × | × |
| 運営者ダッシュボードの閲覧 | ○ | ○ | × | × |
| 受付（自分の参加） | ○ | ○ | ○ | ○ |
| 自分の参加をキャンセル | ○ | ○ | ○ | ○ |
| 他人の参加を除外 | ○ | ○ | × | × |
| 参加者向け表示（live）の閲覧 | ○ | ○ | ○ | △ |
| 「席を決定」操作 | ○ | ○ | × | × |
| 「トーナメント開始 / 一時停止 / 終了」操作 | ○ | ○ | × | × |
| 同じ参加者で次のトーナメントを作る（複製） | ○ | ○ | × | × |
| トーナメント削除（準備中 or 終了） | ○ | ○ | × | × |

凡例: ○ 可 / × 不可 / △ ゲスト匿名は受付完了画面に留め、live 画面には進まない設計

### 4.2 ロール定義（spec 内の文脈で）

- **オーナー**: サークルの最終責任者。トーナメント作成・運営・削除のすべてを行える
- **運営担当者**: トーナメント運営の実務担当。作成・進行・終了処理を行う
- **一般メンバー**: トーナメントに参加できるが、運営機能には触れない。他のメンバーの参加状況を一覧で見ることはできる
- **ゲスト（匿名）**: 受付の「ゲスト参加」経路でサインイン中のユーザー。自分の受付・キャンセルのみ可能

### 4.3 補足

- 受付（自分の参加）はサークル所属を必要としない（招待リンクではなく、トーナメント受付 URL で完結）
- 参加者向け表示は、サークル所属メンバーは制限なし。ゲスト匿名は受付完了画面までで止める
- 一般メンバーが [/tournaments/new](/tournaments/new) や運営者ダッシュボードに直接 URL でアクセスしようとすると、自動的に閲覧可能な画面にリダイレクトされる

## 5. 非機能要件（業務観点）

### 5.1 パフォーマンス（体感）

- 受付の完了は 1 秒以内（参加者がボタンを押した時点）
- 運営者ダッシュボードの表示は 1〜2 秒以内
- タイマー・参加者一覧・席表は他端末の操作が即時に反映される（自動更新）
- 20 人規模・6 卓以下では遅延の体感はない

### 5.2 セキュリティ（運用方針）

- トーナメントの一覧・閲覧はサークル所属メンバーのみ
- 受付 URL（[/join/[tid]](/join/%5Btid%5D)）はサインイン済みなら誰でも開けるため、サークル外の人が偶然アクセスしても受付できる（QR を関係者にだけ配ることで制御）
- 運営操作は運営担当者・オーナーのみ
- 削除は準備中・終了状態に限定（進行中の意図しない消失を防ぐ）

### 5.3 使いやすさ / アクセシビリティ

- ダッシュボードの操作ボタンはアイコン化され、ホバーで意味がわかる
- スマホ / タブレット / PC で動作
- 受付は QR スキャンで素早く開ける
- 参加者向け表示は文字を大きく、色のコントラストを高めて遠見対応

### 5.4 信頼性 / エラー時の挙動

- ネットワーク切断時、運営者ダッシュボードには「接続切れ」のバッジが出て、最後の同期時刻が表示される
- 同時に複数の運営者が操作した場合、まとめて確定される（途中で失敗したら何も変わらない）
- 受付の二重登録は弾かれる（同じ ID で 2 回目は無視）
- 終了済みトーナメントの自動終了は、残り 1 人になった時点で 2 秒後にトリガーされる（手動でも実行可）

### 5.5 保守性 / 運用負担

- ストラクチャの編集と Table 名の変更は別動線（トーナメント編集はストラクチャ未変更でも可）
- 削除はサブコレクション（参加者・卓・イベント）も自動的に巻き取って消える（手動の片付け不要）
- 複製は最大 50 人までという防衛線で、誤操作による大量コピーを防ぐ

### 5.6 互換性

- 過去のトーナメントは現在のフォーマットに自動補完される（表示名・席数・状態など）
- 新規追加されたフィールド（プレイングディーラー / Table 名カスタム など）は既存トーナメントでもデフォルト値で表示される

### 5.7 運用 / 観測性

- トーナメントの状態遷移（準備中 → 受付 → 進行 → 終了）は内部の操作記録に残る
- 終了時刻 / 開始時刻 / 一時停止累積時間 などが記録される
- 障害時は運営者がダッシュボードを再読み込みすることで現状確認できる

## 6. 既知の制約・未対応事項

- **6 卓を超える運用は対象外**: TDA のバランシング許容差が 1→2 に変わるため、本仕様書時点では 6 卓以下で固定
- **複製の上限 50 人**: 過去最大規模を超える運用は想定外（現実のサークル規模では十分）
- **賞金計算は未実装**: 単純分配を含めて v1 では非対応
- **リバイ・アドオンの実行操作は未実装**: ストラクチャに量フィールドはあるが、実行 UI はない
- **観戦モード URL は未実装**: 関係者のみへの URL 配布で代替している
- **PWA 化は未実装**: ブラウザのブックマーク等で代替
